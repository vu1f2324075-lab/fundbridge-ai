# Deploying FundBridge AI

The frontend is a static bundle and the API is a long-running Express server.
They cannot go to the same place, which is the main thing to understand before
starting.

| Part | Host | Why |
|---|---|---|
| Frontend (`frontend/`) | Vercel | Static files; `vercel.json` is in the repo root |
| API (`backend/`) | Render | Needs a persistent process; `render.yaml` is in the repo root |
| Database | Neon | Managed Postgres |
| Proposal files | Cloudflare R2 | Optional at first — see the warning below |
| AI service (`ai-service/`) | not deployed | See "What is left out" |

**The API cannot run on Vercel.** Vercel runs serverless functions, which start
per request and are frozen between them. This API holds a Prisma connection
pool, keeps an in-process rate-limit store, and expects to stay alive. Putting
it behind serverless functions would mean connection exhaustion against Neon
and rate limiting that resets constantly. Render runs it as an ordinary process.

---

## 1. Database — Neon

1. Create a project at <https://neon.tech>.
2. Copy the **pooled** connection string. It has `-pooler` in the hostname.
3. Append `?sslmode=require`.

Use the pooled string, not the direct one. A free instance opens more
connections than Neon's direct endpoint allows, and the failure shows up under
load as refused connections rather than at startup.

---

## 2. API — Render

1. <https://render.com> → **New → Blueprint** → select this repository.
2. Render reads `render.yaml` and creates the API service.
3. It prompts for the values marked `sync: false`:
   - `DATABASE_URL` — the Neon string from step 1.
   - `CORS_ORIGIN` — the Vercel URL from step 3. Leave it for now; come back
     and set it once Vercel has given you a domain.

`JWT_SECRET` is generated by Render itself, so no secret is typed into a
terminal or stored in the repository.

Migrations run from `startCommand` (`prisma migrate deploy`) rather than a
`preDeployCommand`, which Render offers only on paid instance types.
`migrate deploy` is idempotent, so re-running it on each restart applies
nothing.

Note the free instance sleeps after inactivity. The first request after a pause
takes roughly 50 seconds, which during a demo looks like a hang.

---

## 3. Frontend — Vercel

1. <https://vercel.com> → **Add New → Project** → import this repository.
2. Leave the Root Directory as the repository root. `vercel.json` already
   supplies the build command and output directory, so the framework preset
   should stay **Other**.
3. Add one environment variable:

   ```
   VITE_API_BASE_URL = https://<your-api>.onrender.com/api
   ```

   Vite inlines this at **build** time, not at runtime. Changing it later
   requires a redeploy, not just a restart — and if it is missing at build
   time, the bundle ships with an empty API address and every request fails
   against Vercel's own domain.

4. Deploy, then copy the resulting URL back into Render's `CORS_ORIGIN` and
   redeploy the API.

### Why `vercel.json` exists

Without it the build succeeds and the deploy still fails:

```
Error: [STATIC_BUILD_NO_OUT_DIR] No Output Directory named "public" found
```

Vercel looks for `public/` by default. This is an npm-workspaces monorepo whose
frontend builds to `frontend/dist`, so the output directory has to be stated.

Three other things it settles:

- **`npm ci --include=dev`.** Vercel's default `npm install` does not honour the
  lockfile exactly. The first build here produced a 1,209 kB main chunk where
  the same source builds to 678 kB locally — a different dependency resolution,
  nearly double the JavaScript. `npm ci` pins it to the lockfile. `--include=dev`
  is required because Vite and TypeScript are devDependencies and
  `NODE_ENV=production` would otherwise skip them.
- **SPA rewrites.** Everything outside `/assets/` returns `index.html`, so a
  hard refresh or a shared deep link does not 404.
- **Asset caching.** Vite hashes asset filenames, so they are safe to cache
  immutably for a year. `index.html` is deliberately excluded.

## 4. Cookies across two domains — read this one

The frontend ends up on `*.vercel.app` and the API on `*.onrender.com`. Those
are **different sites**, so the browser will not send a `SameSite=Lax` cookie
on any API call.

The failure is silent and easy to misread: login returns 200 and sets the
cookie, and every request after it arrives unauthenticated. Nothing errors. The
app simply behaves as though nobody is signed in.

`render.yaml` therefore sets `COOKIE_SAMESITE=none`, which requires `Secure`
and so is rejected outside production. It also gives up the CSRF protection
`lax` provides for free — acceptable here only because the double-submit CSRF
token is already mandatory on every unsafe method. See
`backend/src/config/cookies.ts`.

The same reasoning applies on Render alone: `onrender.com` is on the Public
Suffix List, so two `*.onrender.com` subdomains are also different sites.

## 5. Uploaded files — do this before anyone relies on it

`render.yaml` ships with `STORAGE_ALLOW_EPHEMERAL=true` so the first deploy
needs no extra accounts. That is a deliberate shortcut, not a finished state.

A Render container's filesystem is replaced on every deploy and every restart.
With the local driver, an uploaded proposal PDF disappears while its database
row survives, pointing at a file that no longer exists. The symptom appears
days later and looks like data corruption rather than a configuration choice.

To fix it, create a Cloudflare R2 bucket and set in the Render dashboard:

```
STORAGE_DRIVER        = s3
S3_BUCKET             = <bucket name>
S3_ENDPOINT           = https://<account-id>.r2.cloudflarestorage.com
S3_ACCESS_KEY_ID      = <R2 API token access key>
S3_SECRET_ACCESS_KEY  = <R2 API token secret>
S3_REGION             = auto
```

Then remove `STORAGE_ALLOW_EPHEMERAL`. The API refuses to start with the local
driver in production unless that variable is present, which is what stops this
being forgotten.

Keep the bucket private. The API streams bytes through its own authenticated,
ownership-checked download route and issues no presigned URLs — a presigned URL
is a bearer token in a query string that leaks through history, logs and
referrers and cannot be revoked before it expires.

## 6. Seeding

The deployed database starts empty. To load the matching configuration and
reference data, run against the production `DATABASE_URL` from a machine that
has the repository:

```bash
DATABASE_URL='<neon pooled url>' npm run db:seed --workspace backend
```

Demo accounts are created only by the local seed and should not be loaded into
a deployment that anyone else can reach.

## What is left out

**The Python AI service is not deployed.** Document extraction, the RAG
assistant and embedding-based retrieval are therefore unavailable; the API
treats the service as optional and `AI_SERVICE_URL` is blank. Every
deterministic engine — readiness, scheme matching, investor matching — is
unaffected, because none of them calls it.

Deploying it needs the ONNX migration first. The current virtualenv is roughly
1.5GB, most of it PyTorch at 539MB, which does not fit a free instance.
